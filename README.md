# 电子神经元超小集群（Electronic Neuron Micro-Cluster）

> **在 8 GB 显存的单机上，让一个 3B 模型拥有一个可检索、可审计、可信赖的外部知识层。**
> 知识问答 **80.0% ±7.5%**（无记忆时 3.6%）；单次延迟 **0.125 秒**；
> 6 小时连压测 **121,428 条请求、0.003% 异常、显存无泄漏**。

---

## 这是什么

一句话：**用「小稠密模型 + 外部记忆库 + 自校验」代替「一个大模型」。**

```
  用户提问
     │
     ▼
  ┌──────────────────────────────────────────┐
  │ L0  记忆层（向量索引 + 唯一真源）           │
  │      · facts.md   结构化事实（带 measured_at）│
  │      · episodes.md 对话片段（每轮一条）       │
  │      · bge-small-zh 做向量化（26 MB）        │
  ├──────────────────────────────────────────┤
  │ L1  可验证性检查                            │
  │      答案必须能在召回文本里找到依据，否则弃答   │
  ├──────────────────────────────────────────┤
  │ L2  基座模型 Qwen2.5-3B Q4（66 tok/s）      │
  ├──────────────────────────────────────────┤
  │ L3  置信度路由（可选）                       │
  │      logprob 低 → 升级到 9B（共驻留，零切换）  │
  └──────────────────────────────────────────┘
```

## 核心数字（全部实测）

| 指标 | 数值 | 样本 |
|---|---|---|
| 知识问答准确率（有记忆） | **80.0% ±7.5%** | 110 条 |
| 知识问答准确率（无记忆） | **3.6% ±3.5%** | 110 条 |
| 不可答时弃答率 | **85%** | 20 条 |
| 无记忆时乱答率 | **100%** | 20 条 |
| 单次延迟 P50 / P95 | **0.125 / 0.175 秒** | 121,428 条 |
| 6 小时压测异常率 | **0.003%** | 121,428 条 |
| 显存漂移 | **无泄漏**（360 次采样） | 6 小时 |
| 并发 | **8 并发零失败，10.9 请求/秒** | 24 条 |
| 代码任务 3B 单跑 | **0.677** | HumanEval 164 |
| 代码任务 3B→9B 级联 | **0.738** | HumanEval 164 |

## 为什么叫「电子神经元」

每个知识单元（一个 key-value 事实，或一轮对话）就是一个**神经元**：

- **独立存储**：一行 markdown，不是塞在模型权重里
- **按需激活**：向量近邻召回，不是全量加载
- **可审计**：你能打开文件看它记住了什么、改它、diff 它
- **可重建**：索引是派生，真源永远是 markdown

这借鉴了小说写作工具 [interactive-novel] 的「状态外置」思想：
**事实外置成唯一真源，视图（索引）随时可从真源重建。**

## 🚩 它**不是**什么（重要）

**它不是「用记忆替代参数」。** 实测证据：

| 维度 | 换参数库能换吗 | 依据 |
|---|---|---|
| **知识**（知道什么） | ✅ 能 | 3.6% → 80.0% |
| **能力**（会不会做） | ❌ 不能 | 代码任务 0.677，加记忆**一点没变** |
| **风格/技能** | ❌ 不能 | few-shot 蒸馏 **+0.000** |

9B 单跑 HumanEval **0.768**，3B 是 **0.677** —— **这个差距记忆填不上**。

> **准确的说法是「3B + 知识库」，不是「更大的 3B」。**
> **它等效的是知识量，不是推理能力。**

## 快速开始

```bash
# 1. 起后端（两个服务）
llama-server -m Qwen2.5-3B-Instruct-Q4_K_M.gguf -c 4096 -np 1 -fa on --jinja \
             --temp 0 -ngl 99 --port 8050
llama-server -m bge-small-zh-v1.5-q8_0.gguf -c 1024 -fa on \
             --embeddings --pooling cls -ngl 99 --port 8044

# 2. 起服务
python serve_mem.py        # -> http://127.0.0.1:8497/
```

打开网页就能问。答案下面会列出**召回依据和相似度分数**，依据不足时会明确说「不知道」。

## 三条必须遵守的设计规则

1. **模型输出的未验证内容不能当事实写入记忆。**
   实测：错答案写进对话记忆后，模型下次读到会照抄，越错越自信。

2. **记忆的写入源必须是外部独立数据，不能是模型自采样。**
   实测：用模型自己的幻觉当记录流，门控 precision = **0.000**。

3. **不同类型的内容不能放同一个向量索引。**
   实测：长文本（对话记录）的相似度天然高于短文本（事实条目），会系统性压过短文本。

## 已知限制

- 知识库规模只验证到 **1 万条**（更大规模未测）
- 真实文档直接建库只有 **70%**（冗余 + 版本冲突，见技术文档）
- **不是生产级服务**：无鉴权、无限流、无进程守护
- 意图映射（问题 → 指标）规则匹配 **81%**，歧义时能力有限

## 适用边界（重要）

**它不是「通用小助手」，是「特定领域的专用助手」。**

| 场景 | 适配度 | 原因 |
|---|---|---|
| 某产品的参数/FAQ 助手 | ✅ **很好** | 知识有限、可穷举、能整理干净 |
| 某项目的规范/流程助手 | ✅ **很好** | 同上 |
| 某语言的 API 查证助手 | ✅ **很好** | 同上 |
| 长文写作（≤2000 字） | ⚠️ 可用 | 需要素材库喂料；3000 字以上不行 |
| 通用聊天助手 | ❌ 不行 | 知识无限、无法穷举 |
| 通用编程助手 | ❌ 不行 | 需要能力，不是知识 |
| 比较/计算型推理 | ❌ 不行 | 实测 1/3（0.18 vs 0.12 判反） |

### 关键：规模不是瓶颈，「干净」才是

| 规模 | 结果 |
|---|---|
| 60 条事实 | 80.0% 准确 |
| 10,000 条事实 | 检索 **0.05 ms**，召回 1.00 |
| 87 份真实文档（527 切片） | **70%** —— 因为同一指标有 23 个副本 |

> **100 条干净、带时间戳的事实，胜过 10000 条混乱的。**

### 最大的隐性成本是「人」

- 整理 100 条干净事实：数小时人工
- 保持不过时：持续人工
- 版本冲突：`memory_check.py` 能报警，**但保留哪个版本要人决定**

**这比显存、比延迟都重要。**
