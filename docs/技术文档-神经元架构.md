# 电子神经元超小集群 —— 技术文档

**版本** 1.0 · **日期** 2026-10-18 · **硬件** RTX 4070 Laptop 8 GB / 16 GB RAM / Windows

---

## 摘要

本文描述一套在 **8 GB 显存的单机**上运行的本地知识系统：一个 3B 稠密语言模型 +
一个向量记忆层 + 一个可验证性检查器 + 一个置信度路由器。

核心主张：**在「知识问答」这一维度上，外部记忆可以把 3B 模型的表现从 3.6% 提升到 80.0%，
而延迟保持在 0.125 秒（P50）。** 但它**不能**提升模型的推理能力。

代码任务上 3B 单跑 0.677、9B 单跑 0.768，这 0.091 的差距记忆填不上。

本文同时记录了 **6 个被实验否定的方案** 和 **5 类会导致系统失效的陷阱**，
因为它们的价值不低于正向结论。

---

## 1. 问题

在 8 GB 显存上，能全量驻留 GPU 的模型上限约 **7 GB ≈ 9B Q4**。可选路径：

| 路径 | 结果 |
|---|---|
| 上更大的稠密模型 | 9B 封顶，且慢 2.6 倍 |
| 用 MoE 换容量 | **否证**：专家落内存后 3.4 tok/s |
| 训练自己的模型 | **不可行**：无训练栈、CPU torch |
| **外置知识 + 小模型** | **本文方案** |

关键观察：**「知道一个事实」和「会做一道题」是两件事。** 前者可以外置，后者不能。

## 2. 架构

```
L0  记忆层       facts.md / episodes.md（唯一真源）+ index.json（派生索引）
L1  校验层       答案必须在召回文本里找到依据，否则弃答
L2  基座层       Qwen2.5-3B-Instruct Q4_K_M（66 tok/s）
L3  路由层（可选） token logprob 低 → 升级 Qwen3.5-9B IQ3_XXS
```

### 2.1 L0：记忆层

**真源是两个 markdown 文件，索引是派生物。**

facts.md 格式（必须结构化）：

```markdown
- `qa130_accuracy` = `0.800`  <-- measured_at: 2026-10-18, n: 110, 说明: 知识问答基准的可答准确率
```

| 字段 | 必要性 |
|---|---|
| key | 唯一标识，查重和引用靠它 |
| value | 实际值 |
| **measured_at** | **判断新旧，治版本漂移的唯一手段** |
| n | 样本量，判断可信度 |
| **说明（中文）** | **查询是中文，只有英文 key 检索不到** |

episodes.md 格式：

```markdown
## 轮次 12 | 2026-10-18 19:21
- 用户：门控在真实噪声下的精度是多少
- 回答：门控精度：0.000
- 依据：gate_precision_real_noise
```

**未验证的回答必须标为「未验证猜测」，不能写成「回答」。** 理由见 4.1。

### 2.2 L1：可验证性检查

三条判据，任一通过即算「有据」：

1. 去空白的原文子串出现在上下文里（处理「华北2」这类中文+数字短答案）
2. 归一化后的答案整体出现在归一化上下文里
3. 答案里的数字/英文 token 全部能在上下文里找到

**注意：token 必须从原始回答提取，不能从归一化串提取。**
归一化会剥掉空格，把 P95 和 0.1745 粘成 p9501745，导致误判。

### 2.3 L3：置信度路由

用单次推理自带的 token logprob 作置信度（**免费**，不需要多次采样）。

**按输出形态分组**维护历史：mean_logprob 对写作类（每 token 仅 0.49 概率）
和代码类（0.99 概率）相差 **65 倍**，用同一份全局阈值会让写作类被 74.6% 无谓升级。

## 3. 理论：为什么它能「小占用、近似大模型」——以及边界

### 3.1 成立的部分

模型的输出可以分解为两部分贡献：

    P(answer) ≈ P_knowledge(知识是否在场) × P_skill(模型会不会用)

**知识项可以外置。** 实测：

| 条件 | 知识问答准确率 |
|---|---|
| 无记忆（知识不在权重里） | **3.6%** |
| 有记忆（知识在上下文里） | **80.0%** |

即：**一个 3B 模型 + 知识库，在知识维度上超过一个没有该知识的更大模型。**

### 3.2 不成立的部分（本文最重要的诚实声明）

**技能项不能外置。** 实测：

| 能力 | 3B | 9B | 记忆能补吗 |
|---|---|---|---|
| HumanEval 代码 | **0.677** | **0.768** | 不能 |
| few-shot 蒸馏代码 | 0.875 | — | **+0.000** |

代码任务在加了完整记忆后**分数一点没变**（0.677 → 0.677）。
few-shot 注入 8 个 9B 的解答，也是 **+0.000**。

**因此对「接不同参数库做不同类型工作」的回答是：**

**换「知道什么」可以，换「会不会做」不行。它等效的是知识量，不是推理能力。**

### 3.3 一个可操作的判据

| 问题 | 结论 |
|---|---|
| 答案是否**存在于某个文档/数据库**里？ | 是 → 知识型，外置有效 |
| 是否要求**只在权重里存在的模式**（语法、推理链、代码技能）？ | 是 → 能力型，外置无效 |

## 4. 关键设计规则（每一条都由实测得出）

### 4.1 模型输出的未验证内容不能当事实写入记忆

**实测事故**：模型答错的 intent_map_accuracy = 0.81 被写进对话记忆，
之后每次检索都把它当历史事实，模型读到自己的错误就照抄。
episodes.md 里堆了 **5 条**同样的错误。

**清理后同一个问题立刻回到正确答案 0.800** —— 检索没变、事实库没变，
只清理了对话记忆。**这是根因的决定性证据。**

**规则**：验证通过写「回答」，不通过写「未验证猜测」，依据记事实的 key 而不是模型的答案。

### 4.2 记忆的写入源必须是外部独立数据，不能是模型自采样

实测：让 3B 在无记忆下对同一批事实采样 K=5，用它自己的输出当记录流：

| 指标 | 数值 |
|---|---|
| 门控收下 | 15 / 30 |
| **收下里正确的** | **0** |
| **precision** | **0.000** |

模型对「超时毫秒数」有先验偏见，5 次全给 300000，门控投 **5/5** 票通过了它。

**对照**：合成随机噪声的漏放率是 **0/600 = 0%**。

**差别不在错误多少，而在错误是否独立。**
**随机错误能被多数投票压掉；系统性偏见只会被多数投票放大。**

### 4.3 不同类型的内容不能放同一个向量索引

实测：把 facts 和 episodes 混在一个索引里时，问「压测的 P95 延迟」，
召回的全是**之前问过同样问题的对话片段**（相似度 0.88~0.92），
真正的 soak_6h_p95_sec = 0.1745（相似度 0.56）被挤出 top-3。
给事实加 0.08 权重**不够**。

**解法**：两个独立索引，事实取 top-1、片段取 top-2，各自排序后合并。

### 4.4 必须用专用检索模型，不能用基座 LLM 的隐状态

| 模型 | pooling | 召回 | 平均领先 |
|---|---|---|---|
| Qwen2.5-1.5B | mean | 4/15 | **-0.0684** |
| Qwen2.5-1.5B | cls | 3/15 | **-0.0491** |
| Qwen2.5-1.5B | last | 4/15 | **-0.0904** |
| **bge-small-zh-v1.5（26 MB）** | **cls** | **13/15** | **+0.0503** |

**「平均领先」为负**意味着正确项的分数低于最强错误项——不是在弱区分，是在往反方向指。

### 4.5 检索键必须包含用户会说的词

原来 facts 只有英文 key qa130_accuracy，查询「知识问答的准确率」**检索不到**。
加中文说明后，top-1 从错变成对（0.7258，领先 0.0816）。

### 4.6 事实只注入 top-1

注入 top-3 时，模型会在两条都叫「准确率」的事实里**挑错一条**（检索对、生成错）。

### 4.7 绝对 logprob 阈值不能跨任务迁移

| 任务 | logprob 中位 |
|---|---|
| 写作（开放式） | **-0.7159** |
| 代码（封闭式） | **-0.0110** |

差 **65 倍**。用同一个绝对阈值，等于把「输出有多开放」误当成「模型有多可能答错」。
必须用**任务内相对分位**。

## 5. 实验与结果

### 5.1 知识问答基准（130 条）

60 条事实 + 110 条同义改写查询 + 20 条不可答查询。

| 组 | 可答准确率 | 95% CI | 不可答时乱答 |
|---|---|---|---|
| A 无记忆 | **3.6%** | ±3.5% | **20/20（100%）** |
| B 有记忆 | **80.0%** | **±7.5%** | 8/20（40%） |
| C 有记忆 + 可验证 | **80.0%** | ±7.5% | **4/20（20%）** |

**可验证性检查不提升答对率，但把「对不存在的东西也敢编」从 40% 压到 20%。**

### 5.2 6 小时连压测

| 指标 | 数值 |
|---|---|
| 请求总数 | **121,428**（5.6 请求/秒） |
| P50 / P95 / P99 | **0.1250 / 0.1745 / 0.1905 秒** |
| 异常 | **4 条（0.003%）**，全部来自人工重启 |
| 弃答率 | **16.8%**（理论值 16.7%） |
| 显存 360 次采样 | 4410 → 4361 MiB，前 1/3 均值 4334 vs 后 1/3 **4362** |

**分 6 段 P50：0.1287 → 0.1237（反而快了 4%），P95：0.1807 → 0.1731。没有任何劣化趋势。**

### 5.3 并发

| 并发 | 成功 | P50 | 吞吐 |
|---|---|---|---|
| 1 | 3/3 | 0.22 秒 | 4.5 请求/秒 |
| 8 | 24/24 | 0.70 秒 | **10.9 请求/秒** |

**零失败。** 并发提升的是吞吐（2.4 倍），单请求延迟变差是排队。

### 5.4 检索规模

| 事实数 | 召回 | 建索引 | 检索 |
|---|---|---|---|
| 100 | 1.00 | 1.4 秒 | 0.000 ms |
| 10,000 | **1.00** | 143 秒 | **0.05 ms** |

**检索成本几乎不随规模增长，瓶颈是线性的建索引。**
（此测试的查询来自 key 片段，**偏易**；真实改写查询是 87%。）

### 5.5 代码任务

| 方案 | HumanEval (164) | 延迟/题 |
|---|---|---|
| 1.5B 单跑 | 0.598 | 4.5 秒 |
| 3B 单跑 | 0.677 | 6.8 秒 |
| 9B 单跑 | **0.768** | 18 秒 |
| **3B→9B 级联（20% 升级）** | **0.738** | **10.4 秒** |

级联用 32% 的额外延迟拿到 67% 的增益，效率是大模型直连的 **2.1 倍**。

## 6. 被否定的方案（负结果）

| 方案 | 否证依据 |
|---|---|
| **MoE 换容量** | `-cmoe` 1.0 tok/s；`-ncmoe 0`（专家全推 GPU）**3.4 tok/s**，比 3B 稠密慢 19 倍 |
| **共享显存当容量** | `-ncmoe 0` 时显存卡在 7440 MiB、速度饱和 3.4 tok/s；带宽等于内存 |
| **多采样级联** | 1.5B×K=3 = 13.5 秒 > 3B 单跑 6.8 秒；判据太贵，结构性失败 |
| **few-shot 蒸馏** | 8 个 9B 解答当教学样本，准确率 **0.875 → 0.875（+0.000）** |
| **参数压缩替代记忆** | 目标精度下所需参数量**省 0%** |
| **1M 上下文** | q4 KV 也要 9.5 GB > 5.5 GB 可用；实测 3B 在 20k 正常、40k 失败 |

## 7. 工程陷阱

| 陷阱 | 现象 | 解法 |
|---|---|---|
| **Windows 端口双重绑定** | 改完代码重启，日志说「就绪」但请求还是旧行为 | SO_REUSEADDR 允许两进程绑同端口；用 netstat 确认旧进程真死，**或直接换端口** |
| **弃答误杀** | 「华南1」这类中文+数字短答案 100% 被弃答 | 加「原文子串出现在上下文里」判据 |
| **token 从归一化串提取** | P95 与 0.1745 粘成 p9501745，误判无据 | 从原始回答提取 |
| **pwsh 不传 workdir** | 找不到脚本 | 显式传 workdir |
| **chat-template-kwargs 被 shell 搞坏** | 服务启动报 usage 错误 | Qwen2.5 无 thinking 模式，去掉该参数 |

## 8. 局限

### 8.1 知识规模与质量

- 只验证到 **1 万条事实**；更大规模未测
- 真实文档直接建库只有 **70%**，主因是冗余 + 版本冲突（同一 0.677 出现在 **23 个切片**）
- **文档转 facts 的整理仍需人工**，这是准确率的决定性因素

### 8.2 能力上限

- 记忆**不能**提升推理/代码/风格能力（见 3.2）
- 意图映射（问题 → 指标）规则匹配 **81%**，歧义时能力有限

### 8.3 工程

- **不是生产级**：无鉴权、无限流、无进程守护、无持久化
- 单流后端 `-np 1`，并发上限约 8
- 上下文实测只到 20k

## 11. 一句话总结

**这套系统的价值不在于「更聪明」，而在于「知道得准、说得有据、不知道就说不知道」。**

**它把模型的「知识」和「能力」分开：知识可以外置、可以审计、可以修正；
能力仍必须来自权重。**

## 12. 附录：能否「接入不同参数库做不同类型的工作」

这是设计者最常问的问题，答案需要分三层。

### 12.1 能换的：知识领域

`.memory/facts.md` 换一套，就是换一个知识领域。**同一套代码、同一个基座**。

| 换成的库 | 能做的事 |
|---|---|
| 运维规范库 | 查端口、超时、发布窗口 |
| 产品参数库 | 查规格、价格、兼容性 |
| 代码 API 库 | 查函数签名、参数含义 |
| 医疗指南库 | 查适应症、剂量（**需专业审核**） |

**这条路我们已经验证**：无记忆 3.6% → 有记忆 80.0%。

### 12.2 不能换的：能力上限

换成任何知识库，**基座的能力不变**：

| 任务 | 换库后 |
|---|---|
| 查一条 API 的定义 | ✅ 有效 |
| 用这堆 API 写一个复杂程序 | ❌ HumanEval 仍是 0.677 |
| 查一条法律条文 | ✅ 有效 |
| 据此写一份辩护词 | ❌ 需要写作能力，库给不了 |

**「知道」和「会用」是两件事。库只解决前者。**

### 12.3 真正可行的「多库」形态

不是「换模型能力」，而是「**按问题路由到不同知识库**」：

```
问题 → 意图识别 → 选库（运维 / 产品 / 代码）
                → 在该库内检索 → 组装上下文 → 同一基座回答
```

**这条路是可行的**，我们的意图映射实测 **81%**（13/16，含 5 个改写问法）。

但要注意：

| 能做 | 不能做 |
|---|---|
| 一个问题只查一个库 | 跨库联查（「运维的端口和产品的端口分别是什么」） |
| 库内有明确 key 的事实 | 需要推理的复合问题（「比上季度高多少」） |

### 12.4 一句话结论

**换库换的是「它知道什么」，不是「它会不会」。**
**同一基座 + N 个知识库，能覆盖 N 个知识领域，但只有一份能力。**

这也正是本项目的定位：**它不是一个更聪明的模型，是一个「知识可替换」的模型。**
