# 接进服务：`.memory/` 驱动的知识服务（2026-10-18）

> 产物：`serve_mem.py`（端口 8497）。**不覆盖原 `serve.py`**，两者可并存对照。

## 一、架构

    请求 -> 检索
             ├── 事实索引（top-3）    ← facts.md
             └── 片段索引（top-2，排除最近2轮） ← episodes.md
          -> 拼上下文 = 最近 2 轮 + 检索结果
          -> 3B 回答 -> 可验证性检查
          -> **自动追加一条 episode 到 episodes.md**

## 二、实测（5 个问题，直接调模块）

| 问题 | 答案 | 判定 |
|---|---|---|
| 压测的 P95 延迟是多少 | **0.1745秒** | ✅ |
| 级联的 pass@1 是多少 | 0.7… | ✅ |
| **知识问答的准确率是多少** | intent_map_accur… | ❌ 答成了意图映射准确率 |
| bge 的召回率是多少 | 0.8… | ✅ |

## 三、过程中修掉的三个 bug（都是实测暴露的）

### bug 1：token 从归一化串里提，被粘连

问「压测的 P95 延迟」，模型答「0.1745 秒」，但被判不可验证。

真因：`norm()` 剥掉空格和标点，把 `P95` 和 `0.1745` 粘成 `p9501745`，
token 提取得到 `"9501745"`，在上下文里找不到了。

**修**：从**原始回答**提 token，不从归一化串提。

### bug 2：对话记忆污染事实检索

问「压测的 P95 延迟」，召回的全是**之前问过同样问题的 episode**（字面更像），
真正的 `soak_6h_p95_sec = 0.1745` 被挤出 top-3。

**修**：事实加 0.08 权重 —— **不够**（episode 相似度 0.88~0.92 vs 事实 0.5~0.6）。

### bug 3（最终解）：事实和片段必须分索引

**修**：两个独立索引，事实取 top-3、片段取 top-2（且排除最近 2 轮，避免重复），
各自排序后合并。改成这样后 evidence 稳定是 `['fact','fact','fact','episode','episode']`。

> **教训：不同类型的内容不能放同一个向量索引里比相似度。**
> 长文本（对话记录）的相似度天然高于短文本（事实条目），会系统性地压过短文本。

## 四、启动时的自检

服务启动会自动：
1. `memory_check.check()`
2. 如果 `index-stale` 或 `index-missing` → **自动 rebuild**
3. 加载索引，打印"记忆 N 条，下一轮次 M"

## 六、诚实边界

1. **HTTP 服务没跑通后台常驻** —— 逻辑用模块直调验证过（4/5），但**网页没在新版上验证**。
2. **只测了 5 个问题**。
3. **`episodes.md` 现在有 7 条**（前几轮测试写入的），会持续增长；**没有清理策略**。
4. **片段参与检索但只取 2 条**，长对话的历史召回能力**没测**。
5. **`add_vec` 只往内存索引追加，不写回 index.json** —— 重启后从 episodes.md 重建即可，但**运行期间崩溃会丢内存里的部分**。
