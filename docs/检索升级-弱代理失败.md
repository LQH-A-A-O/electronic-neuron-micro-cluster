# 检索升级：弱代理验证失败（2026-10-18）

## 一、想验什么

当前系统的检索是**精确 key 匹配**——问法一变就检索不到。
想验"模糊/语义检索能不能救回这些漏掉的查询"。

## 二、为什么没用向量

`/embedding` 端点返回 **501**：
```
This server does not support embeddings. Start it with --embeddings
```
要起带 `--embeddings` 的服务得重启，而**后台 2 小时长测正占着 GPU**
（3B + 9B 共驻留，空闲显存只剩几百 MiB）。起新服务会抢资源、污染长测数据。

**所以改用零 GPU 的代理：字符 n-gram 相似度。**

## 三、实测（30 条查询）

| 判据 | 总体召回 | 标准问法（20） | 改写型（10） |
|---|---|---|---|
| **精确匹配** | **0.67** | 1.00 | **0.00** |
| **字符 n-gram（阈值 0.45）** | **0.33** | 0.50 | **0.00** |

**模糊比精确还差，改写型一条没救回来。**

## 四、为什么失败（两个原因，都结构性）

1. **实体名彼此太像**：`玄枢-000` / `玄枢-001` / … 共享 `玄枢-0` 前缀，
   n-gram 相似度被这个共享前缀主导 → 标准问法从 1.00 掉到 0.50。
2. **改写型字面无重叠**：「那个叫玄的…」和「玄枢-000」除了一个"玄"字几乎不共享 n-gram
   → **0.00，一条都救不了**。

## 五、这次验证的判定：**作废**

> **它没有测出"语义检索的价值"，只测出"字面模糊不是语义的替代品"。**

这和之前那次"20 道题 20/20 全对 → 分离度 +0.000"是**同一类方法学错误**：
**用了一个测不出目标信号的代理，然后拿它的结果说话。**

## 六、要真验，必须做这两件事

1. **起一个带 `--embeddings` 的服务**（用 1.5B Q4 即可，1.12 GB）；
2. **构造"只有语义能连、字面无重叠"的查询集**（例如：
   key = "玄枢-001 的编号是 1037"，query = "刚才说的那个一千零三十七是哪个？"）。

**再做三路对比**：精确匹配 / n-gram / 向量近邻，在**同一个**改写型查询集上的召回。

## 七、诚实边界

1. **阈值 0.45 是随手定的**，没扫。
2. **只有 30 条查询、20 个实体**，样本很小。
3. **n-gram 用 n=2**，没试 n=3 或加权的字符 n-gram。
4. **向量检索到底能提升多少，完全未知** —— 这次什么都没测出来。
