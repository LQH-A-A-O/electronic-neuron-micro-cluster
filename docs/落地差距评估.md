# 距离实际落地还差什么（2026-10-18）

## 一、先说最新一轮：提示词工程救不了"利用"瓶颈

| 注入方式 | 准确率 |
|---|---|
| A 无记忆 | 2/15 = 0.13 |
| **B top-3 裸注入** | **11/15 = 0.73** |
| **C top-1 + 强约束** | **11/15 = 0.73** |
| **D top-3 + 约束 + 编号** | **7/15 = 0.47** |

- **C 打平**：top-1 修好了「老数据能留多久」，但弄坏了「先放多少用户进来」，净零。
- **D 明显更差**：「只能从上面 3 条里选一条」这类指令**干扰了模型**。

> **结论：0.73 这个天花板不是靠改提示词能突破的。**
> 剩余 4 个错里，**2 个是检索失败（抽象问法）、1 个是幻觉、1 个是事实混淆**。

## 三、🚩 距离实际落地还差什么 —— 按"卡脖子程度"排

### 第 1 档：不解决就不能上生产

| # | 缺口 | 现状 | 要做什么 |
|---|---|---|---|
| 1 | **知识规模没验证过** | 只测过 15~300 条；**没测过万/十万条** | 向量检索在 10 万条下的召回率与延迟**完全未知** |
| 2 | **真实语料没验过** | 门控的"零误杀零漏放"是**合成语料**（实体编号，高度可分） | 换成真实文档，门控精度会掉（CIFAR 真实噪声那轮漏放率 0.37~0.47） |
| 3 | **幻觉没有防线** | 模型有上下文还编了个 90 | 需要**答案可验证性检查**（比如答案必须在召回文本里出现） |
| 4 | **没有 API / UI** | 只有 Python 脚本 | 要做成 HTTP 服务 + 简单前端才能被人用 |
| 5 | **单流** | `-np 1`，3017 条是**串行**跑的 | 多人用必须排队或加槽，而**余量只有 ~468 MiB** |

### 第 2 档：能用但不放心

| # | 缺口 | 现状 |
|---|---|---|
| 6 | **评测规模太小** | 15 条查询、15 条知识，**所有端到端数字的置信区间都很宽** |

| 10 | **阈值是手调的** | `ESC_FRAC=0.2`、`WINDOW=20`、`min_score=0.35` 全是拍脑袋，**没扫过** |

## 四、最该先做的三件事（按投入产出比）

1. **答案可验证性检查**（解决幻觉，1~2 小时）
   召回文本里没有的实体/数字，直接判"不知道"。
2. **真实语料上的门控精度**（决定这套东西在真实数据上还成不成立）
   拿一份真实文档 + 人为注入已知错误，测门控的漏放率。
3. **知识规模扫描**（100 / 1000 / 10000 条）
   看召回率和延迟怎么随规模退化——这是"能不能真用"的硬指标。

## 五、诚实边界

1. **所有端到端数字都基于 15 条查询**，统计上很弱。
2. **我自己写的改写查询**可能比真实用户问法更贴近记忆内容。
3. **判分是字符串匹配**，不理解语义等价。
4. **"0 异常"只对 3017 条、2 小时成立**。
5. **上面的"第 1 档"是判断，不是测出来的** —— 我没有在真实规模/真实语料上跑过。
