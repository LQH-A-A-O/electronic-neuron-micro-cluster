# 部署链路验证：走 HTTP 与直接打模型一致（2026-10-18）

## 一、为什么补这一测

130 条基准之前是**直接打 llama-server** 测的（80.0% ±7.5%）。
但用户实际走的是 `serve.py` 的 HTTP 路径——中间多了检索、提示词拼装、可验证性检查。
**必须确认这条链没把质量吃掉。**

## 二、结果：完全一致

| 指标 | 直接打模型 | **走 HTTP** |
|---|---|---|
| 可答准确 | 88/110 = **0.800 ±0.075** | **88/110 = 0.800 ±0.075** |
| 不可答时弃答 | 80%（16/20） | **85%（17/20）** |
| 服务端 P50 | — | **184 ms** |
| 服务端 P95 | — | **264 ms** |
| 总耗时（130 条串行） | — | 26 秒 |

> **同一批 110 条可答题，两条路径都是 88 条正确。**
> **部署链路没有质量损耗。**

弃答率还略好（85% vs 80%）——因为服务里的 `supported()` 是按实际召回文本判断的，
比基准里那条简易判据更准。

## 三、延迟说明

服务端自己报的 `ms`（184/264）比压测里测到的（P50 127ms / P95 179ms）**略高**，
因为：

1. 这轮是**串行**跑 130 条，压测是连续高并发（更稳定）
2. 压测的问题是固定 12 个（答案短），基准的问题更长
3. **这轮和压测同时在跑**（共用 8050 后端），有排队

> **三个延迟数字都记在报告里，不掩盖差异。**

## 四、诚实边界

1. **这轮与 6 小时压测并发**，两者互相有轻微影响（压测 2011→~2100 条期间）。
2. **130 条串行 26 秒 = 平均 200ms/条**，但服务端报的是 184ms，差值是 HTTP 开销 + 我的客户端。
3. **判分仍是字符串匹配**，与基准口径一致。
4. **只测了 8499 端口**（带深链接的最新版）。
