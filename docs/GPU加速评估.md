# 关于「改用 GPU 加速、靠近传统模型硬件架构」的回应（2026-10-17）

## 一、先澄清：**我们最好的结果本来就是纯 GPU 的**

| 模型 | 配置 | tok/s | 权重驻留 |
|---|---|---|---|
| Qwen2.5-1.5B | `-ngl 99` | **98~116** | 100% 显存 |
| Qwen2.5-3B | `-ngl 99` | **66** | 100% 显存 |
| Qwen3.5-9B | `-ngl 99` | **23~28.5** | 100% 显存 |
| Qwen3.6-35B-A3B | `-cmoe`（专家留 CPU） | 1.0~3.4 | 内存 ← **MoE 死在这** |
| Qwen3.6-35B-A3B | `-ncmoe 0`（尽量全上 GPU） | 3.4 | 饱和，共享显存无效 |

**结论：稠密路线从一开始就是 100% GPU 的，CPU 只在 MoE 的专家 offload 里出现过，
而 CPU 内存带宽（15.4 GB/s）正是把 MoE 拖到 1~3.4 tok/s 的原因。**
所以"GPU 加速、不用 CPU 推理"这件事，**方案里已经是这样了，不是待做的改进**。

## 二、GPU 侧还有哪些没榨干的（按可测性排序）

| 项 | 现状 | 预期收益 | 可测性 |
|---|---|---|---|
| **KV cache 量化（`-ctk/-ctv q8_0`）** | **没用** | AGENTS.md 记 9B 从 16.3 → **31.3 t/s**（f16→q8） | ✅ 立刻可测 |
| 更小 KV（`q4_0`） | 未测 | AGENTS.md 说 q4 不比 q8 快，但保真度更低 | 可测 |
| `--fit on` 精确控制层放置 | 用过，会 OOM | 无（`-ngl 99` 已经最优） | — |
| 批处理（`-np > 1`） | 单流 | 提高总吞吐，**不提高单流 tok/s** | 可测 |
| 更大显存 | 8 GB 硬上限 | 模型 >7 GB 就装不下 | 硬件限制 |

> **我自己的基准漏了这一项**：所有 tok/s 数字都是**没开 KV 量化**测出来的，
> 所以 9B 的 23~28.5 是**偏保守**的；开 q8 KV 后按 AGENTS.md 的记录应该能到 ~31。

## 三、但 GPU 加速救不了什么

**硬件（8 GB 显存 + 16 GB 内存）划出的硬边界是**：

1. **模型总量必须 ≤ ~7 GB** 才能全进显存 → 约等于 **9B Q4** 的上限。
   - 这也是为什么 35B-A3B（13.2 GB）无论怎么调都只能到 3.4 tok/s。
2. **共享显存不算容量**：实测 `-ncmoe 0` 时显存占用卡在 7440 MiB、速度饱和在 3.4 tok/s。
   共享那 8 GB 的带宽等于内存，**不是"多出来的 8 GB 显存"**。
3. **模型变大 → 变慢是线性的**：1.5B 98~116 → 3B 66 → 9B 23~28.5，约等于参数量的倒数。
   **这就是"靠近传统硬件架构"的真实代价曲线，没有捷径。**

## 四、所以这个方向该怎么做

**已经做对了的部分**：推理全在 GPU、用 llama.cpp 的标准 CUDA 后端。

**还剩一件值得做的小事**：把 KV 量化补上，重测 1.5B/3B/9B 的 tok/s
（预计 9B 从 23~28.5 提到 ~31，1.5B/3B 小幅提升）。
**这件事能顺带把之前所有"延迟/题"的折算值一起修正**。

**不值得做的**：
- 继续调 MoE 的 offload 参数（上限已经测到 3.4）
- 指望共享显存（带宽等于内存）
- 指望 CPU 推理（15.4 GB/s vs 显存 90~111 GB/s，差 7 倍）

## 五、诚实边界

1. **"开 KV 量化能到 31 t/s"是引用 AGENTS.md 的历史记录，不是本轮实测** —— 要实测才算数。
2. 我的所有 tok/s 都是**短上下文**（`-c 8192`、生成几百 token）测的；
   长上下文下 KV 会变大，速度会掉，**没有测**。
3. **批处理吞吐（`-np`）完全没测**，如果目标是"服务多人"而不是"单人 100 tok/s"，那是另一条优化线。
