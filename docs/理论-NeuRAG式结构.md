# 理论论证：我们能不能造一套 NeuRAG 式的结构

> 参考：Zheng, Liu, Liu. *NeuRAG: End-to-End Neural Knowledge Augmentation via Hyper-Neurons.*
> Findings of ACL 2026, pp. 30324–30343.
> 论文主页 <https://aclanthology.org/2026.findings-acl.1516/> ·
> PDF <https://aclanthology.org/2026.findings-acl.1516.pdf>
> 本机副本：`refs/neurag.pdf`

## 一、NeuRAG 到底是个什么结构

论文图 1 的对比：

| | 现有 RAG | **NeuRAG** |
|---|---|---|
| 知识存什么 | 文本片段 | **LoRA 适配器**（参数） |
| 怎么选 | 一次性/动态检索，**与模型内部状态无关** | **hidden state 驱动**，解码中自适应激活 |
| 怎么用 | 塞进提示词 | **改模型参数** |

它的核心批判是：**检索与生成是隔离的**——检索器不知道模型此刻在想什么。

## 二、和你之前说的想法对不对得上

你说：「将神经元的单位结构单独落到每一个数据库里，相当于每次激活了神经元其次激活数据参数。」

**完全对得上。** NeuRAG 就是：
- 数据库里每一行 = 一个"神经元" = 一个 LoRA
- 激活 = hidden state 选中某几个 LoRA
- "其次激活数据参数" = 被选中的 LoRA 改变模型权重

## 三、我们造不造得出来 —— 分三层拆

### 第 1 层：数据库结构 + 按需激活 ✅ **已经有**

我们的 `GatedMemory` 就是"每个单元独立一行 + 按 key 激活"。实测：
- 1500 条语料 → 600 条脏数据全部被拒（零误杀零漏放）
- 干净记忆让准确率 0.912 → **1.000**

**差别只在"单元里存什么"：我们存事实，它存 LoRA。**

### 第 2 层：hidden state 驱动的激活 ⚠️ **部分可做**

NeuRAG 用 hidden state 选 LoRA；**我们现在的激活是"精确 key 匹配"，这是最弱的一环**
——问法一变就检索不到。

**但我们有一条不训练就能走的近路**：llama.cpp 有 `/embedding` 端点，
能拿到输入的最后隐状态。于是可以：

    存神经元时 -> 把 key 编码成向量存起来
    激活时     -> 把 query 编码成向量 -> 近邻检索 -> 激活最近的几个神经元

**这就是 hidden-state 驱动的激活，只是"驱动"的结果是检索文本而不是改权重。**
这一层**能测**，而且不需要任何训练。

### 第 3 层：用 LoRA 当知识单元 ❌ **本机造不出来**

| 阻塞 | 具体 |
|---|---|
| **训练** | 没有 transformers / peft；torch 是 CPU 版（`cuda.is_available()=False`）；pip 因 truststore 递归 `RecursionError` 装不了包 |
| **时间** | 1.5B 在 CPU 上前反向约 0.09 秒/token → 128k token ≈ **3.2 小时/epoch**，每个知识单元要训一次 |
| **推理** | llama.cpp 的 `--lora` 是**启动时加载**，没有"逐 token 热切换"的 API |

## 四、结论：能造一个"结构同构、载体降级"的版本

| 维度 | NeuRAG | 我们能做的版本 | 差距 |
|---|---|---|---|
| 单元存储 | 每单元一个 LoRA | 每单元一条事实 + 一个向量 | **载体降级** |
| 激活信号 | hidden state | **query 的 embedding 近邻** | **同构** |
| 激活结果 | 改权重 | 改上下文 | **降级** |
| 泛化 | 改权重 -> 能处理没见过的说法 | 检索文本 -> **必须是能检索到的** | **本质差距** |
| 训练成本 | 高（GPU + 每单元训练） | **零** | 我们赢在这 |
| 本机可行性 | ❌ | ✅ | — |

> **一句话：结构能同构（DB + 按需激活 + 相似度驱动），但"激活的结果"只能是上下文，
> 不能是权重。这个降级不是懒，是硬件和训练栈决定的。**

## 五、最该做的那件事（也是唯一能立刻做的升级）

**把"精确 key 匹配"换成"embedding 近邻检索"。**

这是当前系统最弱的一环：
- 现在问「玄枢-001 的编号是多少」能命中；
- 但问「那个编号 4412 叫什么」就检索不到——**因为 key 必须是精确字符串**。

**升级后用同一张 embedding 表就能覆盖同义改写**，而且这是**纯推理**，不需要训练。

具体做法：
1. `/embedding` 端点把每个 key 编码，存成向量表；
2. 查询时编码 query，取 top-k 近邻；
3. 命中的神经元记录注入上下文（还是走门控）；
4. **对比实验**：精确匹配 vs 向量检索，在"同义改写"的查询集上比召回率。

## 六、诚实边界

1. **NeuRAG 的论文数字我没逐条核对**，只读了前两页的方法与动机；它的实验表和消融结论未复核。
2. **`/embedding` 端点能否给"最后一层 hidden state"没实测** —— llama.cpp 的 embedding
   通常是 pooling 后的句向量，**不是逐 token 的 hidden state**，所以严格意义上
   我们的"hidden-state 驱动"是句向量驱动，比论文的层级低。
3. **"embedding 近邻能替代 LoRA"这个判断是推理，不是实测** —— 知识类检索可能有效，
   但**推理类/技能类**（比如会写某风格代码）它一定无效，因为那需要改权重。
4. **llama.cpp 是否支持运行时切换 LoRA 我没查证**，只基于"启动参数加载"的印象。
