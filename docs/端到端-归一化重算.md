## 二、剩下 4 个错，分三类（这个分类比总数有用）

| 类型 | 条目 | 具体 |
|---|---|---|
| **① 检索错**（2 条） | 团队多久碰一次头 | 召回「回滚需要二十分钟」，应为「每周三下午三点开周会」 |
| | 万一主中心挂了去哪 | 召回「数据库主库的端口号是 5432」，应为「灾备机房在深圳」 |
| **② 事实混淆**（1 条） | 老数据能留多久 | **召回是对的**（备份保留策略是**三十天**），但模型答「一周」——串成了记忆里另一条（日志保留时长**为一周**） |
| **③ 幻觉**（1 条） | 入口流量每秒最多放过多少 | **召回是对的**（每秒**一百**次），模型答「90」——纯编 |

> **关键区分：4 个错里有 2 个是"模型没用对召回的上下文"，不是检索失败。**
> 这意味着下一个瓶颈从「检索」转移到了「利用」。

## 三、检索 vs 利用的现行表现

| 环节 | 表现 | 依据 |
|---|---|---|
| **检索** | 13/15 = **87%** | 上一轮实测（正确答案在 top-3 里） |
| **利用** | 11/13 = **85%** | 检索对的 13 条里，模型用对了 11 条 |
| 端到端 | 11/15 = **73%** | 上面两个相乘再扣掉 2 条检索失败 |

> **现在的短板已经不在检索（87%），而在"模型能不能正确使用召回的内容"（85%）。**

## 四、下一步该做的（按证据排序）

1. **减少事实混淆**：top-3 里放进了互相冲突的数字（三十天 / 一周），模型会串。
   → 试试 **top-1**，或者显式标注"这是你要用的那条"。
2. **减少幻觉**：模型有上下文却编了个 90。
   → 加一句"只允许使用上面列出的事实，没有就说不知道"。
3. **修检索的 2 个失败**：都是抽象问法（"碰头"/"挂了"）。
   → 扩充 key 的表述，或用 query 改写。

## 五、诚实边界

1. **15 条查询**，+0.67 的置信区间很宽。
2. **归一化规则是我写的**（"一百"→100、"百分之五"→5），可能过度宽松或不足。
   - 例：A 组掉 1 条是因为归一化后反而对不上，**说明规则有噪声**。
3. **判分仍是字符串匹配**，不理解语义等价。
4. **缓存回答被截断到 80 字**，可能截掉了正确答案。
5. **这轮全是 3B，9B 没参与**。
