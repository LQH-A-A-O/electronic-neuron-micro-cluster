# 上下文上限与"1M 上下文"的判定（2026-10-17）

## 一、先算账：1M 上下文要多少显存

Qwen 系约 32 层 / 8 个 KV 头 / 128 维，KV cache ≈ **64 KB / token（fp16）** 或 32 KB（q8）。

| 上下文 | fp16 KV | q8 KV |
|---|---|---|
| 8k | ~0.5 GB | ~0.26 GB |
| 64k | ~4 GB | ~2 GB |
| **1M** | **~64 GB** | **~32 GB** |

> **1M 上下文在这台 8 GB 显存的机器上物理不可能**，差 4~8 倍。
> 而且这还不算模型权重（3B Q4 已占 2 GB）。

## 二、实测上限（3B Q4）

| 配置 | 结果 | 显存空闲 |
|---|---|---|
| `-c 8192` | ✅ 提示 **5027 token**，1 秒 | 4442 MiB |
| `-c 32768` | ✅ 提示 **20003 token**，**6 秒** | 3557 MiB |
| `-c 65536` | ❌ 实际可用上下文 < 40000 token | — |
| `-c 131072` | ❌ | — |

> **3B 在 20k token 上下文下工作正常（6 秒），上限落在 20k~40k 之间。**
> **距离 1M 差 25~50 倍。**

## 三、"增加训练语料"这条：做不了

用户提到"必要时增加训练语料"。实测环境：

| 依赖 | 状态 |
|---|---|
| torch | 2.14.1+**cpu**（`cuda.is_available()=False`） |
| transformers / peft / datasets / tokenizers | **全缺**，本会话装不了包 |

> **没有训练栈，也没有 GPU 训练能力。增加训练语料 = 需要重新训练 = 在这台机器上不可行。**

**能替代的东西只有一个**：增加**记忆库**（L0 层）的语料，而不是训练语料。
这条路已经验证有效（P5b：+0.088，e2e：1.000），而且不需要训练。

## 四、结论表

| 需求 | 可行性 | 依据 |
|---|---|---|
| **1M 上下文** | ❌ **物理不可能** | KV 需 32~64 GB，机器只有 8 GB |
| 20k 上下文 | ✅ 可用 | 实测 20003 token / 6 秒 |
| 40k 以上 | ❌ 不可用 | 实测失败 |
| **增加训练语料（微调）** | ❌ 不可行 | 无 transformers/peft，torch 是 CPU 版 |
| **增加记忆库语料** | ✅ 有效 | P5b +0.088、e2e 1.000 |

## 五、混合负载：**没测**

这一轮时间用在了上下文上限上，**混合负载（记忆题 + 代码题同一批）仍未测**。
这是"未测清单"上最后一项有价值的测试。

## 六、诚实边界

1. **只测了 3B**，9B-IQ3 的上下文上限没测（它 KV 更大，上限会更低）。
2. **`-c 65536` 那档的失败方式是"实际可用上下文变小"**，而不是 OOM 崩溃 ——
   llama.cpp 在显存不够时会自动缩上下文，**具体缩到多少没查**。
3. **填充文本是重复句子**，真实文本的 token 密度不同，**实际可容纳字数会有出入**。
4. **1M 那个数是按 Qwen 架构估算的**，不是实测（实测不到那么远）。
