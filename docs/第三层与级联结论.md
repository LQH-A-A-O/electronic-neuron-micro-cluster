# 9B 第三层实测 + 一个重要的负面结果（2026-10-17）

## 一、9B 稠密（第三层）的实测

| 指标 | 数值 |
|---|---|
| 吞吐 | **23.0 ~ 28.5 tok/s** |
| **HumanEval pass@1（60 题）** | **0.883（53/60）** |
| 用时 | 249 秒（60 题，约 4.2 秒/题） |

## 二、🚩 关键负面结果：**级联在这批题上不如直接用 9B**

同一批 60 道 HumanEval 题，全部实测量：

| 方案 | pass@1 | 延迟/题（折算） | 复杂度 |
|---|---|---|---|
| 1.5B 单采样 | 0.683 | 4.5 秒 | 最低 |
| 1.5B→3B 级联（75% 升级） | 0.883 | 18.6 秒 | 高 |
| **9B 单独** | **0.883** | **约 18.0 秒** | **低** |
| 1.5B→3B 级联（3% 升级、宽松判据） | 0.717 | 13.7 秒 | 高 |

> **9B 单独跑 0.883 @ 18s，与 1.5B→3B 级联的 0.883 @ 18.6s 完全打平。**
> **级联付出了复杂度，没有任何收益。**

### 为什么？

因为**升级率高达 75%** —— 几乎每道题都要跑第二个模型。
既然第二个模型几乎总会被调用，那第一个模型（1.5B）的 K=3 采样就是**纯浪费**。
级联要赚钱，前提是**升级率低 + 升级目标强**；这两个条件在这批题上都不满足。

## 三、那分层稠密还有没有意义？—— 有，但形态要改

**"用对比决定升级"这个机制本身被验证了**（互证成功组 0.944 vs 失败组 0.619），
但它在这批题上**救不回自己的开销**。所以正确的形态不是"每道题都先跑小的"，
而是：

| 场景 | 用什么 | 依据 |
|---|---|---|
| 交互式、要快 | **1.5B 单独**（4.5 秒，0.683） | 9B 要 18 秒，等不起 |
| 要质量、可等 | **9B 单独**（18 秒，0.883） | 级联打平但不值复杂度 |
| 极难且非交互 | 才考虑级联 | 需要升级率天然很低 |

> **结论：在 HumanEval 这类任务上，"分层"的真正价值是"**按场景选一层**"，
> 不是"每道题动态升级"。动态升级只在升级率天然很低时才划算。**

## 四、这对项目意味着什么

「电子神经元超小集群」里的"集群"，**不应该是"多模型级联"，而应该是"可选的模型梯队"**：

- **必须有**：门控记忆（P5 已验证：0.880 → 1.000）—— 它作用在**输入侧**，不增加推理延迟。
- **可选**：模型梯队（1.5B / 3B / 9B），**按部署场景选一个**，而不是运行时动态切换。
- **不需要**：MoE（已证死）、动态级联（已证不划算）。

**真正还在增值的是记忆层，不是推理调度。**

## 五、诚实边界

1. **60 道题**，0.883 与 0.883 的"打平"意味着都在 ±1~2 题的噪声内。
2. **9B 只跑了 60 题**（不是 164），和 1.5B 的 0.598（164 题）**不可直接比较**。
3. **延迟是折算值**（450 token ÷ tok/s），不是端到端计时。
4. **行为互证没做成**：我的脚本用 `exec` 跑生成的代码却没有超时保护，撞上死循环卡死。
   需要改用子进程 + 超时（像 HumanEval 判分器那样）。
5. **没有测"9B 与级联在同一批题上的逐题胜负"** —— 只比了总数。有可能会级联赢一些、输一些。
