## 二、两个关键事实

### 1. 基座 LLM 的隐状态不是检索向量

Qwen2.5-1.5B 的三种 pooling **平均领先全是负数** —— 正确项的分数**低于**最强的错误项，
即"不是在弱区分，而是在往反方向指"。那 4 次命中是分数打平时的运气。

**原因**：它没有做过对比学习，所有句子的余弦相似度挤在 0.83~0.91 的窄区间。

### 2. 专用检索模型一上就成

bge-small-zh-v1.5：
- **只要 26 MB**（q8_0），不占显存压力
- 召回 **87%**（vs 基座 27%）
- **平均领先翻正**（−0.05 → **+0.05**）
- 正确项均分 0.54（拉开了，不再是 0.9 那么挤）

## 三、这对系统的意义

当前系统的检索是**精确 key 匹配**，改写查询召回 **0%**。换成 bge 之后：

| 场景 | 现在 | 换 bge 后 |
|---|---|---|
| 「玄枢-001 的编号是多少」 | ✅ | ✅ |
| 「那个一千零三十七是哪个」 | ❌ | ✅（87% 概率） |
| 同义改写 / 口语化提问 | ❌ | ✅ |

> **这是"能不能实际用"的分水岭**：精确匹配意味着用户必须记得确切的 key 字符串，
> 而向量检索才是真正可用的检索。

## 四、工程上的落地

    # 起检索服务（26 MB，几乎不占显存）
    llama-server -m bge-small-zh-v1.5-q8_0.gguf --embeddings --pooling cls \
                 -c 1024 -ngl 99 --port 8044

    # 入库：每条神经元记录 -> 向量，存进表
    # 查询：query -> 向量 -> 余弦近邻 top-k -> 取记录

**和现有架构的接法**：把 `GatedMemory.recall(key)` 的精确匹配换成向量近邻，
门控逻辑（多记录互证）完全不变。

## 五、诚实边界

1. **只有 15 条知识、15 条查询**，样本很小；87% 的置信区间很宽。
2. **改写查询是我自己写的**，可能比真实用户问法更"贴近语义"。
3. **只测了 Qwen2.5-1.5B** 的 embedding，9B 没测。
4. **`--pooling` 试了 cls/mean/last**，bge 只试了 cls/mean。
5. **没测长文本检索**（现在全是单句）。
6. **没测中文以外的语言**。
7. **bge 的 26 MB 是 q8_0**，f16 更大但可能更准，没比。
