# 修复：可验证性检查的弃答误杀 bug（2026-10-18）

## 一、怎么发现的

6 小时压测跑到 359 条时，弃答率是 **33.1%**，但压测用的 12 个问题里只有 2 个是"库里没有"的
（应该是 16.7%）。多出来的 16.7% 是**误杀**。

逐题统计：

| 问题 | 表现 | 真值 |
|---|---|---|
| 订单服务的监听端口 | 答 8000 ✅ | 8000 |
| 支付网关的超时毫秒数 | 答 578毫秒 ✅ | 578 |
| **用户中心的部署区域** | **永远弃答** | 华南1 |
| **报表平台的部署区域** | **永远弃答** | 华南1 |
| 临时服务X01/X02 | 弃答 ✅ | 无 |

## 二、根因

原代码：

    if not toks:
        return False if len(norm(ans)) > 0 and len(norm(ans)) <= 2 else True

`norm()` 会把中文全部剥掉，只留数字和英文。所以：

| 答案 | norm 之后 | 长度 | 判定 |
|---|---|---|---|
| `华南1` | `1` | 1 | ❌ **判不可信** |
| `华北2` | `2` | 1 | ❌ **判不可信** |
| `8000` | `8000` | 4 | ✅ 正常校验 |
| `ops-admin` | `ops-admin` | 9 | ✅ 正常校验 |

**所有"中文+数字"的短答案都被 100% 误杀。**

## 三、修复

三条判据，任一通过即算有据：

1. **去空白的原文子串出现在上下文里**（新加，专门处理「华南1」这类）
2. 归一化后的答案整体出现在归一化上下文里
3. 答案里的数字/英文 token 全部能在上下文里找到

## 四、验证（5/5 通过）

| 答案 | 上下文 | 期望 | 实际 |
|---|---|---|---|
| 华北2 | 用户中心…华北2 / 报表平台…华南1 | True | ✅ True |
| 华南1 | 同上 | True | ✅ True |
| **8910** | 消息总线…8105 / 用户中心…8070 | **False** | ✅ False |
| 8000 | 订单服务…8000 | True | ✅ True |
| 华东1 | 用户中心…华北2 | False | ✅ False |

## 五、线上复验

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 用户中心的部署区域 | `{"answer":"不知道","abstained":true}` | `{"answer":"用户中心：华南1","verified":true}` ✅ |
| 临时服务X01的端口 | `{"answer":"不知道"}` | `{"answer":"不知道"}` ✅（仍正确弃答） |

> **误杀修好了，真幻觉仍然拦得住。**

## 六、🚩 顺带发现的第二个坑：Windows 端口可以双重绑定

**现象**：改了代码、重启服务，日志明确显示"就绪： http://127.0.0.1:8399/"，**但请求还是旧行为**。

**原因**：Python 的 `HTTPServer.allow_reuse_address = 1`，而 **Windows 的 SO_REUSEADDR
允许两个进程同时绑定同一端口**（不像 Linux 会报 EADDRINUSE）。于是：
- 旧进程（PID 29000）继续在 8399 上 LISTENING
- 新进程也能绑定成功、打印"就绪"
- **但连接被旧进程抢走**，所以行为没变

`taskkill /PID` 与 `Get-NetTCPConnection | Stop-Process` 都没杀掉它，
最后是 `powershell Stop-Process -Id 29000 -Force` 才清掉。

**教训：Windows 上改完服务代码，必须确认旧进程真的死了（netstat 看到 0 个 LISTENING），
不能只看日志里的"就绪"。**

## 七、诚实边界

1. **压测前 359 条用的是有 bug 的版本**，这部分数据要单独标注。
2. **修复后只做了 2 次 curl 验证**，没有重跑完整 130 条基准。
3. **误杀还有没有别的形态没查**（比如纯英文短答案）。
4. **重启服务会让压测短暂出错**，那几条错误要排除。
