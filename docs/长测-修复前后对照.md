# 2 小时长测：修复前 vs 修复后（2026-10-18）

## 一、结果

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 请求数 | 2395 | 3017 | — |
| 总生成 token | 289,457 | 287,920 | ≈ |
| **P50** | 0.80 秒 | 0.91 秒 | +14% |
| **P95** | **9.01 秒** | **6.15 秒** | **−32%** ✅ |
| 总升级率 | 24.9% | 24.6% | ≈ |
| **写作升级率** | **74.6%**（596/799） | **24.9%**（250/1006） | **−50 个百分点** ✅ |
| **代码升级率** | **0.0%**（0/1596） | **24.5%**（492/2011） | **+24.5 个百分点** |
| 写作 P50 | 7.95 秒 | 4.80 秒 | −40% |
| 代码 P50 | 0.50 秒 | 0.70 秒 | +40% |

## 二、发生了什么

修复让**每类用自己的 20% 分位**当阈值。于是：

- **写作**：不再被代码的高置信拉低阈值 → 升级率从 74.6% 降到 **24.9%**（省时间）
- **代码**：不再被写作的低置信抬高阈值 → 升级率从 0% 升到 **24.5%**（花时间）

**总升级率几乎没变（24.9% → 24.6%）。**

## 三、这算不算变好？—— 算，而且是关键的方向纠正

**因为两类的升级价值完全不同**：

| 类 | 升级有用吗 | 依据 |
|---|---|---|
| **代码** | ✅ **有用** | HumanEval 164 题：3B 0.677 → 级联 **0.738** |
| **写作** | ❌ **没用** | 早期质量探针：9B 写作 7/12 < 1.5B 的 9/12 |

> **修复把"没用的升级（写作 74.6%）"换成了"有用的升级（代码 24.5%）"，
> 总预算不变，P95 反而降了 32%。**

## 四、🚩 但暴露出一个新的设计局限

**分位阈值 = 固定预算，不是难度信号。**

每类永远会升级大约 ESC_FRAC（20%）的请求——**不管这批请求是难还是易**。
也就是说：系统现在是"**每类花 20% 的慢模型预算**"，而不是"**只在真不确定时才升级**"。

实测印证：代码类升级率 24.5%，接近 20% 的设计值，**与题目实际难度无关**。

### 要变成"难度驱动"，得改用绝对阈值（按类标定）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **分位阈值（当前）** | 自动适应分布漂移，无需标定 | **预算固定，与难度脱钩** |
| 绝对阈值（按类标定） | **真按难度升级** | 换模型/换任务要重标；分布漂移会失准 |

**两个都该有**：用绝对阈值做主判据，用分位做兜底（防止阈值漂到 100% 或 0%）。

## 五、诚实边界

1. **两次长测不是同一批请求**（修复后多跑了 622 条），任务序列相同但长度不同。
2. **P50 变差（0.80→0.91）** 是代码类升级率上升的直接后果，**这是有意识的取舍**。
3. **写作没有判分**，"写作升级没用"仍是引用早期 18 题探针，不是这次测的。
4. **只跑了 2 小时**，没测更长时间。
5. **显存走势没在这份报告里（见 soak2_vram.jsonl）**。
6. **0 异常的结论只对 3017 条成立**。
